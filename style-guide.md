# Style guide

These are the actual habits behind my documentation, pulled from what I already do across my projects, not a list of aspirations.

## Voice and tone

- Write like you're explaining it to a person, not filing a report. Short sentences, plain words, and explain any jargon the first time it shows up.
- Keep it warm but professional. 
- Say what something is in one plain sentence before getting into detail.

## Structure

- Put a live demo link and a screenshot near the top, before the detail starts. Let people see it before they read about it.
- Explain the why behind a decision, not just the what. A "why I built it this way" note is more useful than a bare list of dependencies.
- Be honest about limitations. What doesn't work yet is as useful to a reader as what does, and it builds more trust than pretending everything is finished.
- Give setup steps as commands to copy and paste, not a paragraph explaining them.
- When a concept might be unfamiliar to some readers, add a short plain-terms explanation rather than assuming everyone already knows it.

## Formatting

- No long dashes. Use commas, periods, or parentheses instead.
- Sentence case for headings, not title case.
- One idea per bullet point.

## How AI fits into writing documentation

- I use Claude and ChatGPT to draft first-pass documentation from the actual code, then compare what each one produces.
- I check the draft against how it actually works, fill in what's missing, and rewrite it so it sounds like me.
- AI gives me a starting point. I'm responsible for what's accurate and what sounds like me.
